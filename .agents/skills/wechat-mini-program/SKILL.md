# 0. 强制计划模式

**重要：在执行任何其他操作前，必须切换到计划模式。**

在进入计划模式前，不得实现、编辑、创建、删除、安装或修改任何内容。

每次调用此技能时，计划模式都是必须执行的第一步。

计划中必须先分析并呈现：

- 业务目标、用户角色和核心流程
- 微信小程序与 H5 的交付关系及技术选型
- 原生微信小程序、Taro 或 uni-app 的技术选型
- 页面、组件、Feature、分包和依赖方向
- 微信平台能力、浏览器能力与后端接口边界
- 状态管理、缓存和离线策略
- UI / UX 方向、设计系统和可用的前端设计技能
- AI 原生文档、Skills 和 ADR
- 测试、性能、体验评分和质量门禁
- 小程序审核、H5 部署、环境和 CI/CD 注意事项
- 将要创建或修改的文件、目录、实施顺序和风险

必须先将计划呈现给用户，获得确认后再实施。如果当前代理支持原生计划模式，应使用该模式；否则先输出计划并等待确认。

## 计划阶段的最小输入

如果业务描述不完整，先补齐以下信息；无法获得时，明确写出合理假设：

- 小程序名称、目标平台和业务类型
- H5 是否为同等重要的正式产物，是否需要独立域名、SEO 或分享落地页
- 主要用户、核心页面和最高频操作
- 是否需要登录、支付、定位、地图、扫码、订阅消息或文件上传
- 是否需要多端复用、后台管理端或服务端渲染替代方案
- 后端接口、鉴权方式、部署环境和预计规模

# 1. 业务分析

开始编码前先分析：

- 核心业务、用户角色、业务流程和异常流程
- 页面数量、层级、TabBar、子包和独立分包需求
- 首屏性能、弱网、低端设备和离线缓存要求
- 登录、手机号、用户信息、隐私协议和权限授权时机
- 支付、退款、订单、优惠券、积分和风控需求
- 定位、地图、扫码、相机、相册、蓝牙、NFC 或订阅消息需求
- 文件上传、图片压缩、预览、下载和临时文件生命周期
- 实时数据、消息推送、数据可视化和长列表需求
- 多端复用、原生能力差异和未来扩展方向
- H5 入口、浏览器兼容范围、响应式断点和 SEO / 社交分享需求
- 微信审核规则、隐私合规、域名白名单和运营要求

优先设计最短、最稳定的核心用户路径，同时为拒绝授权、接口失败、超时、重复提交、登录失效和版本更新提供明确处理。

# 2. 技术选型

先确定交付模式，再选择实现方案。交付模式至少明确：

- 微信小程序为主，H5 作为配套落地页或分享页
- 微信小程序与 H5 同等重要，共享主要业务流程
- 微信小程序为主，H5 仅提供降级或管理入口

实现方案只在以下方案中选择，且必须说明理由：

- 原生微信小程序：WXML、WXSS、JavaScript/TypeScript
- Taro：React 或 Vue 跨端方案，可输出微信小程序与 H5
- uni-app：Vue 生态跨端方案，可输出微信小程序与 H5
- 原生小程序 + 独立 H5：共享领域、服务和类型，平台入口分别实现

从以下维度比较：

- 是否需要微信专属能力和平台 API 的完整可控性
- 是否需要复用 H5、App 或其他小程序代码，以及可接受的复用边界
- 团队熟悉的语言、框架和构建工具
- 包体积、首屏性能、分包能力和平台兼容风险
- 组件生态、调试体验、类型安全和 AI Coding Agent 可理解性
- 微信审核、版本发布、灰度和长期维护成本
- H5 域名、HTTPS、部署、SEO、浏览器兼容和缓存更新成本

先输出：

1. 选型结论
2. 业务与技术依据
3. 为什么不选择其他方案
4. 关键技术风险与验证方式

除非有明确理由，不得引入多套跨端框架，也不得为了“跨端”牺牲核心微信体验。

如果同时支持小程序和 H5，必须明确哪些代码共享、哪些代码隔离：

- 共享：领域类型、业务规则、Service、Repository、数据转换、Design Tokens 和无平台副作用的组件逻辑
- 隔离：页面入口、路由、登录授权、支付、存储、文件选择、地图、分享和平台生命周期
- 适配：通过 Adapter / Facade 暴露统一能力接口，禁止在领域层直接判断 `wx`、`window` 或运行平台
- 产物：分别生成小程序构建产物和 H5 构建产物，分别验证体积、性能、权限和发布配置

# 3. 技术栈与工程约束

根据选型固定并记录实际技术栈。推荐优先使用：

- TypeScript 严格模式
- 原生微信小程序或项目既有的 Taro / uni-app 版本，并记录 H5 输出配置
- Less、SCSS 或 WXSS 变量体系，保持项目样式方案一致
- Zustand、Pinia 或项目已有状态方案；简单状态优先使用页面和组件本地状态
- axios 或项目已有请求库；原生小程序可使用统一封装的 `wx.request`
- ahooks 或项目已有 Hook 工具；不得为小功能增加依赖
- ESLint、Prettier、TypeScript、单元测试和构建检查

约束：

- 严格 TypeScript，禁止无理由使用 `any`
- 页面、组件、Hook、Service 和 Store 职责清晰
- API 必须通过统一请求层访问，页面不得直接散落请求实现
- 所有微信授权、浏览器 API 和平台 API 调用必须集中封装，便于测试和替换
- 统一处理 baseURL、超时、鉴权、刷新登录态、错误映射和请求取消
- 统一处理 loading、empty、error、permission、disabled 和更新状态
- 不得直接把 App 全局状态当作业务数据库
- 不得未经确认升级核心框架、修改构建链或新增重量级依赖

# 4. 架构与设计模式

架构优先考虑健壮性、可复用性、可维护性、可扩展性和可测试性，并遵循 SOLID、DRY、KISS、单一职责、依赖倒置和开闭原则。

复杂业务优先使用 Feature / Domain 组织代码：

```text
src/ 或项目根目录
├── app/                 # 应用入口、生命周期、全局配置
├── pages/               # 页面入口，只负责组合页面能力
├── features/            # 按业务域组织的功能模块
│   └── example/
│       ├── components/
│       ├── hooks/
│       ├── services/
│       ├── repositories/
│       ├── store/
│       ├── types/
│       └── constants/
├── components/          # 跨业务复用组件
├── services/            # 请求客户端和跨域服务
├── adapters/            # 微信 API、存储、支付等平台适配器
├── platforms/           # 小程序与 H5 的入口、路由和平台实现
├── store/               # 少量全局状态
├── utils/               # 无业务副作用的工具
├── styles/              # Design Tokens 和全局样式
├── types/               # 全局类型
├── config/               # 环境和运行配置
└── tests/               # 测试辅助和契约
```

推荐职责链：

```text
Page
↓
Feature Components
↓
Hooks / Use Cases
↓
Service / Repository
↓
Request Client / Platform Adapter / External Systems
```

按实际变化点选择模式：

- Repository：隔离 API、缓存和本地数据来源
- Adapter：隔离 `wx.*`、Taro、uni-app 与业务代码
- Service Layer：编排登录、订单、上传等业务流程
- Strategy：隔离不同支付、登录、上传或分享策略
- Factory：创建不同业务类型的表单、卡片或数据转换器
- Facade：向页面提供简单的微信能力入口
- Observer / Event-driven：处理登录态变化、版本更新或跨页面事件

双端项目必须额外定义平台能力契约，例如 `AuthProvider`、`StorageProvider`、`PaymentProvider` 和 `ShareProvider`。小程序与 H5 各自实现契约，业务流程依赖接口而不是具体平台。

不要为了展示设计模式而抽象。每个重要决策都说明：

```text
问题
→ 变化点
→ 抽象边界
→ 使用的设计模式
→ 为什么选择
→ 如何扩展
→ 如何测试
```

避免巨型页面、巨型 Store、巨型 Service、页面直接请求 API、重复业务逻辑、全局状态滥用和循环依赖。

# 5. 页面、路由与分包

实现页面前先建立页面地图：

- TabBar 页面与普通页面
- 页面入参、返回值和来源
- 页面栈行为、重定向和登录保护
- 主包、普通分包、独立分包和预下载策略
- 页面生命周期、重复进入和退出清理
- 分享入口、扫码入口、模板消息或外部跳转入口
- H5 路由、深链接、刷新恢复、登录回调和分享落地页

分包原则：

- 高频首屏能力放在主包
- 低频、大体积或相对独立的业务放入分包
- 通过构建产物检查主包体积，不凭感觉拆包
- 分包页面不得隐式依赖主包页面状态
- 预下载只用于确定会访问且值得提前加载的路径
- H5 不使用小程序分包概念替代 Web 代码分割；按路由和首屏需求配置懒加载
- H5 刷新、前进后退、未知路由、分享参数和未登录重定向必须有明确行为

页面不得承担复杂业务逻辑。新增页面必须处理：

- 首次加载、刷新、分页和骨架屏
- 空数据、接口错误、重试和网络恢复
- 未登录、授权拒绝、权限不足和登录过期
- 重复点击、并发请求、表单校验和离开确认
- iPhone 安全区、刘海屏、键盘遮挡和不同屏幕尺寸
- H5 响应式布局、浏览器兼容、键盘行为、横竖屏和桌面宽屏显示

# 6. 微信平台能力

所有平台能力先确认官方 API、权限、审核和隐私要求，再实现统一适配层。微信专属能力在 H5 中必须提供降级、替代入口或明确不可用状态：

- 登录：`wx.login`、服务端换取会话、登录态缓存和失效恢复
- 用户信息：遵循最新用户信息与隐私授权规则，不诱导或强制无关授权
- 手机号：明确业务必要性、授权入口和服务端校验
- 支付：统一订单创建、支付调起、回调确认、幂等和失败重试
- 位置与地图：权限前置说明、拒绝降级、坐标和隐私处理
- 上传与媒体：大小、格式、压缩、进度、失败重试和临时文件清理
- 订阅消息：模板、授权时机、发送条件和用户可撤回路径
- 分享与扫码：来源参数校验、深链路恢复和异常兜底
- 版本更新：`wx.getUpdateManager`、强制更新策略和灰度风险
- 本地缓存：容量、过期时间、敏感数据保护和版本迁移
- H5 登录：OAuth / 扫码登录 / 业务登录回调，禁止假设 H5 可以直接复用 `wx.login`
- H5 支付：根据业务与平台选择微信网页支付、二维码支付或跳转策略，并由服务端确认结果
- H5 能力降级：定位、扫码、文件选择、分享和订阅消息必须有浏览器可行替代方案

禁止把敏感密钥、支付密钥、服务端凭证或业务权限判断放在小程序客户端或 H5 前端。所有关键权限和金额必须由服务端最终校验。

# 7. API、数据与状态管理

统一请求层至少集中处理：

- 环境 baseURL 和合法域名要求
- 超时、重试、请求取消和网络状态
- access token、登录态刷新和并发刷新锁
- HTTP 错误与业务错误的统一转换
- 脱敏日志、请求链路标识和错误上报
- 分页、游标、缓存和数据失效策略

推荐数据流：

```text
Page
↓
Feature Hook / Use Case
↓
Repository
↓
Request Client
↓
Backend API
```

小程序与 H5 必须共享领域数据契约，但不得共享不兼容的生命周期和存储实现。服务端返回的数据应由统一类型和转换层约束，避免两个端各自解释同一字段。

状态分层：

- Local State：输入、弹层、临时 loading 和组件交互
- Feature State：当前业务域的筛选、草稿、列表和流程状态
- Global State：用户会话、应用配置和确有跨页面必要的状态
- Server State：优先由请求层、缓存层或 Feature Hook 管理

# 8. UI / UX 与设计系统

凡涉及 UI / UX、页面视觉、布局、交互或设计系统，必须先检查当前 AI 编程代理环境中的可用 Frontend Design Skill；存在匹配技能时优先读取并遵守，但不得因此改变项目既定技术栈。

设计流程：

```text
检查 UI Skill
→ 阅读 Design System
→ 分析用户和使用场景
→ 确定视觉方向
→ 检查已有组件和页面模式
→ 优先复用
→ 使用小程序组件或 H5 组件实现
→ 编写 WXSS / CSS / 项目样式模块
→ 完整处理页面状态
→ 检查可访问性、性能和一致性
```

Design Tokens 至少统一管理：

- 品牌色、语义色、背景色和文本色
- 字号、字重、行高、间距和安全区
- 圆角、边框、分割线、阴影和层级
- 按钮、输入框、单选、多选、标签和弹层
- 导航、列表、卡片、空状态、骨架屏和错误状态
- Toast、Modal、Action Sheet、Loading 和权限提示

小程序 UI 额外关注：

- 触控目标足够大，不能只依赖精细鼠标交互
- 交互反馈及时，避免无反馈的异步操作
- 长列表使用分页、虚拟化或分段渲染，避免一次性渲染过多节点
- 键盘、底部 TabBar、状态栏和安全区不遮挡内容
- 权限说明必须在真实业务动作附近出现
- 不堆叠默认组件形成页面，不复制页面后只修改颜色
- 完整处理加载、空状态、错误、禁用、权限和审核限制
- 小程序与 H5 共享 Design Tokens，但允许针对触控、鼠标、键盘和屏幕宽度做平台化交互调整
- H5 需要处理可访问性、焦点、语义化、浏览器标题、favicon 和社交分享元信息（业务需要时）

# 11. 开发规范

新增页面必须遵循：

```text
阅读项目文档
→ 阅读相关 Skill
→ 检查已有 Feature / Component / Hook / API / Adapter / Store
→ 检查页面地图、分包、H5 路由和 Design System
→ 识别可复用能力与变化点
→ 设计页面状态、平台能力边界和微信授权降级
→ 实现
→ 处理 Loading / Empty / Error / Permission
→ 类型检查、Lint、Test、小程序构建、H5 构建和双端验证
→ 必要时更新文档 / ADR / Skill
```

禁止：

- 不看已有代码直接重做页面
- 页面直接调用 `wx.request` 或散落调用微信 API
- 把 token、密钥、金额校验或权限判断仅放在客户端
- 未说明原因就申请敏感权限
- 复制组件后只做微小样式修改
- 为简单页面过度拆分或引入复杂状态库
- 忽略弱网、授权拒绝、登录过期和重复提交
- 未经检查就把大量资源或低频页面放进主包
- 只验证小程序而不验证 H5，或只验证桌面浏览器而不验证移动端 H5

# 12. 质量检查

完成后必须执行并记录可用的检查：

### 架构

- 是否违反目录职责和依赖方向
- 是否存在循环依赖、巨型模块或重复业务逻辑
- 是否正确隔离微信平台能力和外部服务
- 分包边界和页面跳转是否合理

### 类型与代码质量

- 严格 TypeScript 是否通过
- 是否存在无理由的 `any`、类型断言和未处理异常
- ESLint、格式化、单元测试和构建是否通过

### 小程序体验

- 主包体积、首屏、长列表和图片资源是否合理
- 是否在开发者工具和至少一种真机环境验证
- 是否检查不同屏幕、安全区、键盘和弱网
- 是否覆盖加载、空、错、权限、登录过期和更新状态

### H5 体验

- H5 路由、刷新、前进后退、深链接和登录回调是否正常
- 是否检查移动端、桌面端、主流浏览器、键盘和响应式断点
- 是否完成首屏、代码分割、资源缓存、错误页和网络异常验证
- 业务需要时，标题、SEO、Open Graph、favicon 和分享预览是否正确
- 微信专属能力是否提供替代入口、降级状态或清晰提示

### 微信平台与合规

- 小程序合法域名、AppID、隐私协议和用户授权是否配置正确
- H5 HTTPS、域名、跨域、Cookie / Token、隐私协议和第三方脚本是否配置正确
- 权限申请是否必要、可解释且有拒绝后的降级路径
- 支付、手机号、定位和文件等敏感能力是否服务端复核
- 是否检查分享、订阅消息、隐私保护和审核限制

### 文档

- 架构、分包、平台能力和环境变量是否记录
- 重要决策是否新增或更新 ADR
- 新增可复用流程是否补充对应 Skill

# 13. CI / CD 与发布

项目基础开发和双端质量检查通过后，先询问用户：

> 项目基础开发已经完成，是否需要我继续配置 CI/CD、微信小程序体验版 / 正式版和 H5 部署发布流程？

未获得确认不得自动创建 GitHub Actions 或发布配置。获得确认后，根据实际平台生成：

- 依赖安装、类型检查、Lint、测试和构建工作流
- 主包体积、H5 资源体积和双端构建产物检查
- 测试、预览版、体验版、H5 staging 和正式版环境区分
- 微信开发者工具 CLI 或 CI 上传流程
- AppID、私钥、上传密钥等 Secrets 说明
- 版本号、构建号、灰度、回滚和发布记录
- README 中的部署、环境变量、审核和发布说明
- H5 静态资源部署、HTTPS、域名、缓存更新和回滚说明

任何上传或正式发布动作都必须先确认目标环境和版本，不得默认为生产环境。

# 14. 最终输出顺序

严格按照以下顺序输出：

1. 业务分析
2. 技术选型
3. 架构、分包与 H5 路由设计
4. 微信与浏览器平台能力设计
5. 设计模式选择
6. AI 原生工程设计
7. UI / UX 与设计系统
8. 完整目录结构
9. 完整脚手架代码
10. 示例业务模块
11. 示例页面
12. 开发规范
13. 小程序与 H5 测试、审核与发布检查
14. AI 自检清单
15. 询问是否需要配置 CI/CD、微信发布流程和 H5 部署流程

## 最终原则

> AI 优先，但不是只有 AI。
>
> 小程序与 H5 代码不仅要能运行，还要让人类容易维护，让 AI 能快速定位、可靠修改、持续扩展，并通过文档、Skill、ADR 和双端发布检查保持长期上下文一致性。
